# 职途 AI 项目交接

> 更新日期：2026-07-24。本文面向首次接手项目的开发者、产品同学和面试官；它解释系统现在能做什么、Agent 如何工作，以及下一步应从哪里继续。

## 1. 项目定位

职途 AI 是一个本地优先的求职辅助 Web 系统。它把简历、岗位 JD、面试训练、投递机会和复盘串为一条可追踪的求职链路。核心差异不在于增加一个聊天框，而在于全局求职 Agent 能读取当前业务上下文、调用受限工具、给出下一步，并把写操作收敛为用户确认后的提案。

本地开发默认监听 `127.0.0.1` 并使用 SQLite。生产采用 Cloudflare Access allowlist、
Ubuntu FastAPI、PostgreSQL 与 R2；不得把本地认证模式直接公开。

## 2. 用户如何理解产品

- **右侧求职 Agent**：承接对话、上下文读取、工具调用和提案预览。
- **求职指挥台**：展示待确认动作、机会进展、行动项和阶段阻塞，不是第二个 Agent。
- **简历实验室**：上传、版本化、诊断、JD 匹配和生成可确认的新版本。
- **面试训练场**：题目、回答、训练记录和复盘。这里的“AI 教练”仅服务单次练习反馈，不与全局 Agent 重复争夺入口。

## 3. Agent 架构与实际执行链路

```text
页面输入 + module / resume_id / opportunity_id
  -> FastAPI Principal 校验并固定可信用户
  -> ContextBuilder 重建权威业务上下文
  -> MemoryStore 检索相关记忆与待续任务
  -> LocalPolicy 或 RemoteModelPolicy 决策
  -> AgentOrchestrator 在预算内调用 ToolRegistry
  -> 结果综合 / ActionProposalService 生成提议
  -> 用户预览、编辑、确认
  -> 领域服务执行、幂等回执、业务时间线反馈
```

运行时位于 `utils/agent_runtime/`：

- `ContextBuilder` 从业务表重新读取当前简历、机会、看板、训练和行动信息，前端不传递可篡改的完整事实。
- `MemoryStore` 区分工作、摘要、语义、情景、任务和实时业务六类记忆；整份简历和 JD 仍以领域表为准。
- `AgentOrchestrator` 有 4 次工具调用上限、60 秒总时长、单工具超时与重复调用防护，边界触发时返回已取得的可靠结果，不无限循环。
- `ToolRegistry` 当前注册 22 个 JSON Schema 校验的工具，工具只处理用户可见的业务能力。
- `ActionProposalService` 把所有写入限制为“提议 -> 预览 -> 用户确认 -> 领域服务执行 -> 幂等回执”，模型无法直接写数据库，也不能自行指定用户身份。

这不是标准 ReAct 实现：系统不展示或依赖隐藏思维链。远程模型使用供应商原生 `tool_calls`；本地策略用确定性多工具计划。当前也没有引入 LangChain/LangGraph，因为项目的主要难题是本地业务事实、确认边界和可恢复执行，不是编排框架缺失。多 Agent 并行、跨服务长流程或可视审批状态图成为真实需求时，再在适配层评估 LangGraph。

## 4. 无 API Key 与配置 API Key 的区别

| 场景 | 路由方式 | 能力边界 |
| --- | --- | --- |
| 未配置 Key | `LocalPolicy` 意图规则、槽位补全、确定性多工具计划与本地模板综合 | 可完成简历/机会/看板/训练的查询、诊断、匹配、行动建议和事实保真草稿；不伪装成大模型自由推理 |
| 已配置 Key | 确定性任务仍本地优先；开放表达和完整简历深度改写转给 GLM、DeepSeek 或 Kimi/Moonshot | 模型会通读经授权的简历上下文，进行更自然的表达、结构重写和开放问题理解；远程超时或不可用会回退本地策略 |

因此“本地可用”不等于“离线大模型”。它保证核心求职工作流可运行；高质量的开放表达和深度改写仍由用户选择配置的模型提供。

## 5. 工具与外部边界

22 个工具中大部分调用项目内部的 Python 领域服务和 SQLite，例如简历读取/诊断、JD 解析、岗位匹配、训练评估、机会看板、职业报告与待确认操作。它们不是任意执行外部命令，也不提供任意本地文件读取。

确实存在两类受限的外部能力：

- `web_search`：调用 DuckDuckGo Instant Answer API（`https://api.duckduckgo.com/`），只用于用户明确需要时效性公开资料的搜索。
- `fetch_webpage`：对指定的公开 `http/https` 文本网页做受限读取。它拒绝回环、私有地址、内网和无效 URL；不跟随重定向，只读文本内容，设置网络超时和 256 KB 响应上限。

此外，配置 GLM、DeepSeek 或 Kimi/Moonshot API Key 后，开放式请求会把必要的对话和上下文发送给对应模型提供商。核心简历、投递、训练和记忆数据默认不依赖外部工具；外网能力不是完成主流程的前置条件。

## 6. 本轮已完成的产品与展示更新

- 将 Agent 从“AI 教练”中明确拆出：全局 Agent 处理跨模块行动，教练只处理单次训练复盘。

- 强化无 Key 本地策略、远程超时回退、工具预算和中文反馈，降低答非所问、工具循环和英文内部信息泄露的风险。

## 7. 接手与验证入口

## 8. 已知限制与后续路线

短期优先项：

- 建立固定的 Agent 评测集，覆盖无 Key 路由、简历选择、工具计划、超时回退和中文回复质量。
- 为远程模型请求补充可观测指标：提供商、耗时、失败分类、回退比例和人工确认率。
- 扩展 JD/岗位信息的导入与归档，但继续保持外部抓取的 URL 安全边界和用户触发原则。

中期方向：

- 在认证、权限、加密与数据隔离完成后再考虑多用户和云同步。
- 引入后台任务队列，用于耗时简历改写、批量 JD 分析与报告生成，并保留可恢复的任务状态。
- 仅当出现真实的多 Agent 协作、跨服务长流程和可视审批图时，评估以适配层接入 LangGraph；不得绕过现有领域服务、提案确认和 SQLite 事实来源。

## 9. 维护原则

新增功能遵循“先领域契约和测试，再 API，再 Agent 工具，最后界面”。任何写工具只能创建提议；任何外部网络能力必须有明确用户意图、超时和安全限制；任何文档和展示页中的技术描述都应与代码中的真实边界保持一致。
