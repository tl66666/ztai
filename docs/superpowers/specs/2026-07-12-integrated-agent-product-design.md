# JobHunter 全链路 Agent 求职系统设计

日期：2026-07-12  
状态：总体方向已确认，书面规格待复核

## 1. 背景

项目已经具备简历管理、JD 匹配、简历优化、模拟面试、语音分析、题库训练、投递追踪、职业报告和独立 AI 教练页面。现有 Agent Runtime 也已经支持结构化工具调用、持久化多会话、滚动摘要、用户画像、待完成任务、任务经历、实时业务统计和运行审计。

当前主要问题不再是“有没有功能”，而是功能之间没有形成统一业务对象和稳定反馈循环：

- Agent 的 13 个工具几乎都是读取或即时计算工具，不能创建简历版本、保存岗位、创建投递、推进阶段、建立训练任务或保存报告。
- JD、简历版本、匹配、面试和投递之间主要通过前端临时输入框传值，没有共享的“求职机会”上下文。
- Agent 页面与业务页面分离。建议按钮多数只负责跳转，不能携带完整任务状态，也不能让用户预览并确认业务写入。
- 面试进行中状态保存在进程内，服务重启后丢失；部分分析结果只即时返回，没有成为可检索的业务事实。
- Agent 画像只可靠抽取目标岗位、城市和薪资，实时业务上下文主要是数量统计，无法回答“这个岗位应该用哪版简历、最近卡在哪里、下一步做什么”。
- 业务接口、Agent 工具和旧工具类存在重复算法，结果可能不一致。
- `app.py` 承担数据库、业务规则、AI 调用和 HTTP 路由，已不适合继续直接堆叠功能。
- 真实数据中存在旧状态“面试中”，前端固定看板不识别该状态，导致记录在数据库和 Agent 中存在、在页面中却不可见。
- 准备度会被操作次数抬高。当前数据中面试成绩明显偏低，页面仍可显示高准备度。
- 浏览器会请求三个错误的模块背景地址并产生 404。
- 一键启动脚本会尝试结束占用 5000 端口的进程，不应在陌生用户电脑上主动终止无关程序。

## 2. 产品目标

系统应从“多个求职工具加一个聊天页”升级为“围绕每个求职机会持续推进的可执行 Agent 工作台”。

完成后用户可以：

1. 建立长期职业画像、主简历和求职目标。
2. 保存一个真实岗位机会，包括公司、岗位、JD、来源和关键日期。
3. 让系统选择或生成与该岗位对应的简历版本，并保存匹配证据。
4. 根据该岗位和简历建立面试训练计划，跨重启继续训练。
5. 记录投递、笔试、面试、Offer 或拒绝反馈，并形成下一步行动。
6. 在任何业务页面呼出 Agent，自动携带当前机会、简历和模块上下文。
7. 预览、修改、确认或取消 Agent 提议的业务操作。
8. 让业务结果自动反哺画像、任务、薄弱项和后续建议。
9. 在未配置模型 Key 时继续完成确定性任务，并明确区分本地规则与模型生成结果。
10. 在 Edge、Chrome 和 Firefox 上完成核心求职流程；不支持的语音能力必须有文字和文件上传替代路径。
11. 下载项目后通过 Windows 一键启动脚本完成环境检查、依赖安装、端口选择、服务启动和默认浏览器打开。
12. 通过规范、无隐私数据的 GitHub 仓库和静态展示页说明真实功能、技术设计、运行方法和验证证据。

## 3. 技术决策

### 3.1 暂不引入 LangChain 或 LangGraph

继续使用现有轻量 Agent Runtime，并强化它与业务服务的连接。

原因：

- 当前瓶颈是业务对象、可执行工具、统一数据写入和前端审批，不是缺少编排框架。
- 现有运行时已经具备原生 `tool_calls`、严格参数校验、任务续接、预算、审计和分层记忆。
- 增加 LangChain 会引入重复抽象和更多安装依赖，不利于一键启动和课程项目讲解。
- 领域服务、工具协议和记忆接口保持独立；未来出现多 Agent、后台长任务、人工审批图或复杂分支恢复时，可以只替换编排层为 LangGraph。

### 3.2 保持 Flask、SQLite 和原生前端

本轮不迁移前端框架，也不引入外部数据库。优先修复业务边界和产品闭环，控制安装成本。SQLite 使用事务、索引、外键检查、版本化迁移和 FTS5；FTS5 不可用时回退到结构化字段与 `LIKE` 检索。

### 3.3 保持本地单用户定位

当前版本定位为本地单用户求职工作台，不在本轮引入注册、登录和云端同步。所有业务 API 与 Agent API 都由服务端固定到本地用户，不能信任客户端提交的任意 `user_id`。README 和页面明确本地数据边界；若未来公开部署，再独立设计认证、授权、加密和多租户隔离。

## 4. 总体架构

```text
业务页面 + 全局 Agent 助手 + Agent 指挥中心
                    |
              Flask HTTP API
                    |
        ---------------------------
        | 统一领域服务与事务边界   |
        | Profile / Resume         |
        | Opportunity / Interview |
        | Action / Insight         |
        ---------------------------
             |              |
        SQLite 业务数据   Agent Tool Adapters
             |              |
        Domain Events --> Agent Runtime
                           |-- working/session memory
                           |-- semantic profile memory
                           |-- episodic outcome memory
                           |-- task/action memory
                           `-- live business facts
```

HTTP 路由和 Agent 工具只能调用领域服务，不能各自复制 SQL 和评分算法。领域服务负责权限、校验、状态迁移、事务、事件记录和返回结构；API 负责解析请求与序列化响应；Agent 工具负责把模型参数映射为领域命令。

## 5. 领域模型

### 5.1 职业画像

新增 `career_profiles`，每个本地用户一条：

- 主要求职方向、目标岗位、目标城市、期望薪资、经验阶段。
- 已确认技能、偏好、限制条件和更新时间。
- 字段来源分为用户确认、业务证据和系统推断；推断不能覆盖用户确认事实。

页面选择的求职方向必须写入职业画像，不再只保存在浏览器本地存储。

### 5.2 简历与版本

保留 `resumes` 表并增加：

- `parent_resume_id`：指向来源版本。
- `version_label`：例如主简历、测试岗版、某公司定制版。
- `target_job_title`、`application_id`：说明版本用途。
- `status`：`draft`、`active`、`archived`。
- `source_type`：上传、手工、Agent 生成。

分析、优化、定制都通过 `ResumeService`。生成内容默认形成草稿版本，用户确认后保存，不直接覆盖原简历。版本详情显示来源、目标岗位、修改摘要和可对比文本。

### 5.3 求职机会

现有 `job_applications` 作为机会主表继续演进，避免重复数据和高风险重命名。新增：

- `jd_text`、`source_url`、`channel`。
- `resume_id`、`priority`、`contact_name`、`contact_info`。
- `next_action_at`、`interview_at`、`deadline_at`。
- `rejection_reason`、`offer_details`。
- `created_by` 和标准时间字段。

统一状态枚举：`意向`、`准备中`、`已投递`、`简历筛选`、`笔试`、`一面`、`二面`、`HR 面`、`Offer`、`已拒绝`、`已结束`。迁移时把“面试中”等旧值映射到最接近阶段；无法判断的值保留可见并标记待确认，绝不能从看板消失。

`job_matches` 增加 `application_id`、完整 JD 快照和结构化详情，确保未来能解释某次分数基于哪份简历和哪版 JD。

### 5.4 面试与训练

新增持久化 `interview_sessions`：

- 会话、用户、机会、简历、岗位、模式、当前阶段、状态和更新时间。
- 完整状态 JSON 只保存流程状态；可查询字段单独列出。
- 每次回答即时保存，完成后汇总到现有 `interviews` 结果表。

题库练习、语音记录和模拟面试统一产生训练事件，包含能力维度、证据、分数和建议。Agent 可以读取趋势并创建复练任务，但不能把一次规则分数当成确定能力结论。

### 5.5 行动、报告与事件

新增：

- `action_items`：任务类型、标题、关联机会、截止时间、状态、来源和完成证据。
- `career_reports`：阶段、结构化快照、报告正文和生成来源。
- `domain_events`：业务动作、实体、前后状态摘要、来源和时间。
- `agent_action_proposals`：待确认操作、参数、预览、风险级别、过期时间、幂等键和执行结果。

业务写入与事件必须在同一事务中完成。事件只记录必要摘要，不复制完整简历和录音。

## 6. Agent 能力

### 6.1 统一工具来源

现有读取工具改为领域服务适配器，保证页面与 Agent 使用同一算法。保留联网搜索和网页读取的 SSRF、超时与大小限制。

读取工具覆盖：职业画像、简历版本、机会详情、JD 匹配、训练趋势、语音摘要、行动项、准备度依据和阶段报告。

### 6.2 可执行写工具

新增受控操作：

- 保存或更新职业目标。
- 创建求职机会并保存 JD。
- 生成并保存简历草稿版本。
- 关联机会与简历版本。
- 创建面试训练计划或继续未完成面试。
- 创建、完成或调整行动项。
- 更新投递阶段、关键日期和反馈。
- 保存阶段求职报告。

模型不能直接执行写工具。第一步生成 `agent_action_proposal`，前端展示影响范围和字段差异；用户确认后由独立执行接口重新校验所有权、状态、过期时间和幂等键。删除、覆盖、标记拒绝和结束机会属于高风险操作，必须二次确认。Agent 永远不能自动向招聘网站投递、发送消息或访问本地私有地址。

### 6.3 计划与连续任务

Agent 将复杂目标拆为可观察行动项，例如：

```text
完成某公司测试岗申请
1. 保存 JD
2. 选择主简历
3. 完成匹配并生成定制草稿
4. 用户确认简历版本
5. 完成一轮岗位模拟面试
6. 创建投递记录和跟进日期
```

每一步绑定业务实体和完成条件。页面操作完成后，领域事件自动更新任务，不依赖用户回到聊天页口头说明。

## 7. 分层记忆

保留现有记忆层并增强检索和写入来源：

- Working：当前运行状态、工具观察和未完成槽位。
- Session：最近消息和滚动摘要。
- Semantic：用户明确确认的目标、偏好、限制和稳定技能。
- Episodic：已完成任务、关键反馈和结果摘要。
- Task：跨页面行动计划、当前步骤和阻塞原因。
- Business facts：从职业画像、简历、机会、匹配、训练和行动表实时读取。

业务事实不复制成长记忆。检索先按用户、实体和任务过滤，再结合 FTS5 相关性、时间衰减、确认级别和来源可信度排序。删除业务实体后，相关记忆只保留不含原文的审计摘要；清空聊天不删除业务数据。

职业画像的长期事实由显式表单、用户确认的 Agent 提议和明确语言写入。系统推断以候选事实展示，必须经过确认才能影响关键决策。

## 8. 准备度与建议

准备度改为证据加权而不是次数累加：

- 简历质量与完整度：25%。
- 最近真实 JD 的匹配和证据缺口：20%。
- 最近面试成绩、完成度和趋势：25%。
- 题库与语音训练的质量趋势：15%。
- 机会推进、反馈记录和行动及时性：15%。

缺少主简历时总分上限为 30；没有真实 JD 时上限为 55；最近完整面试明显低分时不得标记为“可投递”。返回值必须包含每个分项、数据时间、限制条件和可执行下一步，避免给出无法解释的单一分数。

## 9. 前端体验

### 9.1 全局 Agent 助手

所有主页面提供同一个上下文助手入口：桌面端为可收起侧栏，窄屏为底部抽屉。它显示当前职业方向、机会、简历和模块上下文，并允许用户移除不想发送的上下文。

Agent 回复支持：

- 普通建议。
- 可审计工具事件。
- 行动提议预览，包含确认、编辑和取消。
- 关联实体链接，直接打开对应简历、机会、面试或任务。
- 连续任务进度和阻塞信息。

独立 Agent 页面保留并升级为求职指挥中心，展示活跃机会、行动计划、最近复盘和多会话，不再是单纯放大的聊天框。

### 9.2 机会工作区

投递看板中的机会可以进入详情工作区，按概览、JD 与匹配、简历版本、面试准备、时间线组织。JD 页面产生的结果不再只写入临时 DOM；用户可保存为机会，随后带入简历和面试。

### 9.3 兼容与无障碍

支持范围：

- Microsoft Edge 当前稳定版及前两个主版本。
- Google Chrome 当前稳定版及前两个主版本。
- Mozilla Firefox 当前稳定版及前两个主版本。
- Safari 作为尽力兼容目标，不承诺 Windows 不存在的能力。

基础 CRUD、简历分析、JD 匹配、文字面试、投递和 Agent 聊天不得依赖浏览器私有 API。

语音能力采用能力检测：

- Web Speech API 不可用时隐藏语音转文字入口，并保留文字输入。
- MediaRecorder 按 `isTypeSupported` 选择 WebM/Opus、Ogg/Opus 或浏览器支持格式。
- 不能录音时允许上传现有音频；不能直接播放的格式提供下载和明确提示。
- 所有图标按钮有可访问名称，键盘可操作，焦点可见，弹层可关闭。
- 桌面与 390px 窄屏不得横向溢出、遮挡或依赖悬停完成关键操作。

使用 Playwright 分别在 Chromium、Edge channel 和 Firefox 验证核心流程；机器没有 Edge 时记录为环境跳过，不能伪装为通过。

## 10. 一键启动与可移植性

保留 `start.bat` 作为双击入口，调用 `start-jobhunter.ps1`。脚本必须：

1. 只使用 `$PSScriptRoot`/脚本目录构造路径，不包含开发者绝对路径。
2. 检测 `py -3`、`python` 和可用 Python 版本，要求 Python 3.10 及以上。
3. 检测 pip；依赖缺失时征用当前解释器安装项目依赖，并显示网络/权限错误的可执行解决方法。
4. 不终止占用 5000 端口的未知进程；优先从 5000 开始选择空闲端口，并把实际 URL 传给应用和浏览器。
5. 使用健康检查等待服务就绪，失败时保留日志并显示日志位置。
6. 用系统默认浏览器打开地址，确保 Edge、Chrome、Firefox 默认设置均可工作，不写死浏览器路径。
7. 只清理脚本自己启动的子进程；窗口关闭或 Ctrl+C 时不影响其他程序。
8. 对未安装 Microsoft Word 的电脑明确启用低保真 Word/PDF 回退，不把可选 Office 能力当作启动条件。
9. 路径包含中文、空格、括号时仍能运行。
10. 提供 `-NoBrowser`、`-Port`、`-SkipInstall` 和诊断模式，方便测试和高级用户。

新增干净环境启动冒烟测试：临时路径复制必要文件、选择随机端口、启动、请求健康接口、关闭自身进程。Windows CI 验证 PowerShell 脚本；Python 核心在 Windows 和 Ubuntu 验证，README 说明一键脚本主要面向 Windows。

## 11. 展示页与仓库规范

### 11.1 展示页

`static/showcase.html` 是 GitHub Pages 静态展示，不伪造在线后端。它应包含：

- 产品名称和真实一句话定位。
- 完整求职闭环和 Agent 如何参与每一步。
- 实际系统截图或轻量视频，内容与当前版本一致。
- 架构、工具、记忆、确认写入和本地隐私说明。
- Edge/Chrome/Firefox 兼容范围。
- 下载、启动、模型配置、演示路径和仓库链接。
- 测试数量、浏览器验收和已知限制，避免宣传性虚假承诺。

首屏资源控制体积，视频提供 `poster`、静音和减少动态效果适配；图片转换为合理尺寸的 WebP/PNG。删除确认未引用的重复大文件，保留双主题真正使用的资产。展示页在 GitHub Pages 子路径下使用相对 URL，不依赖站点根路径。

### 11.2 文件与隐私

- 运行数据、数据库、上传、导出、日志、浏览器截图、API Key 和 `.env` 不进入 Git。
- 不提交真实个人简历、电话、邮箱、录音或招聘联系人信息。
- `.env.example` 只包含占位符和说明。
- 增加 `docs/ARCHITECTURE.md`、`docs/USER_GUIDE.md`、`docs/TESTING.md` 和 `CHANGELOG.md`。
- README 保持中文主文档，说明运行方式、功能边界、架构、浏览器兼容和故障排查。
- 依赖文件使用可复现的兼容范围；发布前在干净环境验证实际解析版本。
- 生成资产和开发输出放入约定目录，不在仓库根目录制造临时文件。

## 12. 错误处理与安全

- 所有写接口校验本地用户、实体所有权、状态迁移和输入长度。
- 上传使用安全文件名、扩展名与内容限制；原文件路径不能被客户端控制。
- Agent 写入使用提议、确认、幂等和审计；过期或已执行提议不能重复执行。
- 联网工具继续拒绝本机、环回、私网、链接本地地址和过大响应。
- 模型超时、限流和鉴权失败返回稳定错误码；本地规则不能冒充远端模型成功。
- API Key 不写入数据库、日志、URL 或 Git；页面只显示是否已配置。
- 当前 CORS 仅允许本地服务所需来源，公开部署前不得沿用无约束配置。
- 数据迁移先备份用户数据库，失败时停止启动并提供恢复路径，不在半迁移状态继续运行。

## 13. 测试与验收

### 13.1 自动化层级

- 领域单元测试：状态迁移、准备度、版本创建、任务完成和事件写入。
- 数据迁移测试：旧数据库、旧状态、重复迁移和失败回滚。
- API 集成测试：所有 CRUD、所有权、异常输入、文件上传和 Agent 提议确认。
- Agent 合同测试：读取/写入工具 Schema、审批、幂等、任务续接、业务事件回流和无 Key 策略。
- 浏览器 E2E：职业画像、简历、JD、定制版本、面试恢复、机会推进、Agent 跨页面操作。
- 启动测试：中文/空格路径、端口冲突、依赖缺失提示、健康检查和自有进程清理。
- 展示页测试：GitHub Pages 子路径、坏链接、资源 404、移动端和减少动态效果。

测试不得调用真实付费模型。远端模型协议使用模拟响应；真实 Key 只用于人工可选验收。

### 13.2 完成标准

- 现有功能和历史数据迁移后可用。
- 数据库、页面、领域服务和 Agent 对同一实体给出一致结果。
- Agent 能完成至少一条经过用户确认的“保存 JD -> 创建定制简历草稿 -> 建立面试任务 -> 创建/推进投递”链路。
- 页面业务操作会更新 Agent 的实时上下文和任务进度。
- 未完成面试在服务重启后可继续。
- Edge、Chrome、Firefox 核心文字流程通过；不支持的语音能力有明确降级。
- 桌面和 390px 窄屏无横向溢出、关键遮挡和不可操作控件。
- 浏览器控制台没有项目自身产生的 404 和未处理异常。
- 一键启动在新的 Windows 用户目录、中文/空格路径和端口冲突场景通过。
- 仓库不包含密钥、运行数据库、个人资料和未引用的大型生成文件。
- README、用户指南、架构、测试文档、展示页和代码行为一致。
- 全部自动化验证通过后才允许推送 GitHub。

## 14. 实施拆分

### 子项目 A：数据一致性与领域服务

修复资源和旧状态问题，建立迁移机制，抽取统一领域服务，持久化面试状态，重做证据加权准备度。该阶段完成后现有页面行为保持可用，业务数据有单一事实来源。

### 子项目 B：可执行 Agent 与业务记忆

用领域服务改造现有工具，增加行动提议与确认、行动项、领域事件、丰富业务事实和连续任务。该阶段完成后 Agent 能安全推进业务，而不只是查询。

### 子项目 C：全局协作前端与跨浏览器

增加全局上下文助手、机会工作区、行动预览和指挥中心；完成语音能力检测、Edge/Chrome/Firefox 兼容和响应式验收。

### 子项目 D：便携启动、展示和发布

重写安全的一键启动流程，增加干净环境冒烟测试，整理资产与文档，更新展示页，执行隐私与仓库审计，最后推送 GitHub。

四个子项目依次实施，每个子项目都必须保持可运行、通过对应测试并独立提交。GitHub 推送只在 D 阶段全部发布门禁通过后执行。

## 15. 非目标

- 不自动登录或操控招聘网站，不自动向招聘者发送消息。
- 不引入多用户云部署、支付、订阅或团队协作。
- 不引入向量数据库、消息队列、Celery、Docker 或微服务。
- 不为了“显得智能”展示模型私有思维链。
- 不承诺离线安装第三方 Python 依赖；无网络时提供清晰诊断和手动安装说明。
- 不保证没有 Microsoft Word 时保持复杂 Word/PDF 排版完全一致。
